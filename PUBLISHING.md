# Publishing ntfy private push

Original recipe code is owner-approved MIT. ntfy uses the Apache-2.0 option with its complete tagged license and asset attribution inventory retained; no upstream server, browser dependency, font or sound is relabeled. Keep [ntfy](https://ntfy.sh/) links in every public README. Default qualification covers authenticated HTTP push/replay, not VAPID/mobile-provider delivery, HA or production sizing.

1. Publish only a mechanically compared sanitized source under `tech-progress/ntfy-private-push`, root `/`, real `release-v1` compatibility branch and immutable `v1.0.0` tag. Exclude FINDINGS.md, internal evidence, caches/dependencies, runtime state, credentials and all private authoring history.
2. Run structural/unit/offline graph tests and the isolated local workload/ACL/token/cache/restart/cold-volume restore/retention smoke. Preserve actual runtime defaults and generated-secret expressions; deterministic evaluator output is not a credential generator.
3. Verify the actual selected repository source in Railway. Generate a draft from a correctly named owned source project `ntfy-private-push`. If only the reusable-repository generator rejects an otherwise successful source, a bounded image seed may provide the named shell, never the final source. Restore the complete ID-keyed graph, exclusive source and root, exact probes, PORT8080, public HTTP8080, one exclusive `/var/lib/ntfy` volume, every default/reference/generator and matching descriptions.
4. Fetch and audit the stored serializedConfig after an authorized Composer update. Deploy that **queried stored graph** with templateDeployV2 in a fresh verification environment. Require intended release/revision SUCCESS and current healthy replicas, denial and scoped authenticated publish/read, token/cache persistence through restart, finite retention, and measured workload headroom.
5. Stop/cancel every owned source/verification deployment; poll zero active/current running instances and queued work. Remove domains, services, environments, test volumes and temporary remote/local SSH keys. A deleted project or successful volumeDelete is not proof that retained platform volume rows have completed deletion: read owned volume statuses directly where authorized, and keep the draft unpublished while storage deletion remains pending or unverified.
6. Publish only after all gates pass, using MARKETPLACE.md and its product icon/category/specific45–75-character description. Read back PUBLISHED and the exact identity/settings/config. Add live id/code/source only to an internal publication handoff fragment after success; never claim success for a held draft.
7. The catalog coordinator alone merges the root registry and runs selective marketplace synchronization plus the complete live audit. Catalog publication remains incomplete before that shared gate passes. No authoring-monorepo commit or branch mutation is needed.
