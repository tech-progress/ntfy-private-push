# Upgrade and rollback

Template release **v1.0.1**, recorded in VERSION, is separate from upstream ntfy 2.28.0. This patch changes documentation and docs verification only; the pinned image, startup/auth configuration, defaults and deployment graph are unchanged. It requires no new runtime setting or schema migration. This release must be qualified independently. Maintainers must qualify its frozen source before promotion; a source release does not prove marketplace publication.

The immutable `v1.0.0` in [tech-progress/ntfy-private-push](https://github.com/tech-progress/ntfy-private-push) identifies commit `08089b9848557308275a05c80de581f1a8e81cb8`. Its selected-source Railway proof is historical, not a final stored-template or `v1.0.1` recovery result. Maintain root `/` and compatibility channel `release-v1`; create each immutable SemVer tag once and never move historical tags. Major template releases break the deployment contract, minor releases add compatible behavior, and patch releases fix compatible packaging/docs/security issues.

1. Pause publishers/subscribers and stop the single service before taking a full `/var/lib/ntfy` snapshot. Include auth.db, cache.db, optional webpush.db and every SQLite journal/WAL file; preserve permissions. Store the encrypted backup off-volume, and keep bootstrap credentials, tokens and optional VAPID settings separately secured. Do not archive running SQLite files or delete the production volume as an upgrade step.
2. For an actual ntfy upgrade, read [upstream releases](https://github.com/binwiederhier/ntfy/releases), update the exact image tag and manifest digest together, rebuild, and review schema/CLI compatibility. The wrapper uses v2.28.0 CLI flags including `--ignore-exists`; verify them against the new runtime. Keep a matched prior image and backup for rollback.
3. Use one replica and a stopped-writer replacement. Preserve the same volume and bootstrap variables. Startup resets the bootstrap account to non-admin, replaces its topic grants, clears anonymous grants and reapplies the supplied password. Existing client tokens are not revoked by changing the password; revoke them explicitly when rotating access. Audit other manually created users separately.
4. Check anonymous/wrong-password denial, off-namespace rejection, scoped Basic/token access, cache replay and restart. Independently restore the full snapshot into a distinct empty volume with the same credentials and verify denial/token/replay again before reconnecting clients. Restoring expired messages does not extend their retention. HTTP health alone is insufficient.
5. New SQLite schemas may not permit binary downgrade. Roll back against a compatible schema, or restore the matched old backup into a separate empty volume and use its matched old image. Do not point an older binary at migrated files without upstream compatibility evidence.

Repeat the final source/stored-graph/recovery/headroom gates in [PUBLISHING.md](PUBLISHING.md). There is no rolling, HA, zero-downtime, production RPO/RTO or optional browser-provider recovery guarantee. Preserve VAPID keys and subscriptions when testing optional browser push separately. Never run global Docker cleanup; remove only disposable resources you own.
